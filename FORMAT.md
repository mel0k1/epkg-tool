# FORMAT.md — файловые форматы epkg-tools

Версия спецификации: 1.1 (2026)

Этот документ описывает три формата, необходимые для работы epkg-tools
и для создания собственных репозиториев:

1. `.epkg` — пакет (tar.gz + PKGINFO)
2. `index.json` — индекс репозитория
3. `epkg.conf` — конфигурация клиента

---

## 1. Пакет `.epkg`

`.epkg` — это обычный **gzip-сжатый tar-архив (ustar)**. Всё содержимое
распаковывается в корень файловой системы (`root` из epkg.conf).

### Требования к структуре

| Элемент | Обязателен | Порядок |
|---|---|---|
| `PKGINFO` | да | **первая запись архива** |
| каталоги (`usr/bin/` и т.п.) | по необходимости | в алфавитном порядке |
| файлы | по необходимости | в алфавитном порядке |
| symlink'и | по необходимости | после файлов, в алфавитном порядке |

* Типы записей tar: обычный файл (`'0'`), каталог (`'5'`),
  symlink (`'2'`, цель — в поле `linkname`). Хардлинки и прочие типы
  при установке пропускаются.
* Симлинки подчиняются **политике** `symlinks` из epkg.conf
  (см. раздел 3): `deny` — пропустить с предупреждением (по умолчанию),
  `keep` — создать как есть. Цель symlink'а сохраняется дословно и
  никогда не разыменовывается при распаковке.
* Пути в архиве — относительные, без ведущего `/`, без `..`
  (проверяется при установке; нарушение = отказ установки).
  В режиме `keep` дополнительно запрещено любому элементу пакета
  лежать *под* symlink'ом того же пакета (защита от записи сквозь
  собственный symlink за пределы root).
* Конец архива — стандартные два нулевых блока tar.
* Итоговый поток: gzip (RFC 1952).

### PKGINFO

Формат — построчные пары `key = value`. Обязательные поля:

```
pkgname = hello          # имя пакета, [a-z0-9_-]
pkgver   = 1.0-r0        # версия, произвольная строка без пробелов
```

Необязательные поля:

```
pkgdesc  = Friendly demo # описание (одна строка)
arch     = any           # архитектура
deps     = libfoo, libc>=2.0, bar = 1.1   # зависимости через запятую
```

Токен зависимости:

```
имя            # просто имя
имя=1.0        # точная версия
имя>=1.0       # не ниже (также имя<=, имя>, имя<)
```

Пробелы вокруг имени/оператора/версии допустимы. Сравнение версий —
посегментное: числовые сегменты сравниваются численно (`1.2.10 >
1.2.9`), суффиксы-релизы учитываются (`1.0-r1 > 1.0-r0`), разделители
(`.` `-` `_`) равны между собой, если совпадают. Авто-upgrade уже
установленных зависимостей не делается: если установленная версия не
удовлетворяет ограничению — это ошибка конфликта.

Поле `sha256` добавляется/обновляется **автоматически** утилитой
`mkepkg` и не пишется руками:

```
sha256 = <64 hex-символов>
```

### Манифест-хеш PKGINFO.sha256

Это хеш **содержимого файлов** пакета, независимый от сжатия и от
порядка байтов tar. Он позволяет epkg обнаружить порчу распакованных
данных даже если весь `.epkg` скачался по валидному индексу.

Алгоритм (для каждой обычной записи-файла в **порядке архива**,
кроме самого `PKGINFO`):

```
h = SHA256()
для каждого файла F:
    h.update(u32le(strlen(path(F))))
    h.update(path(F))
    h.update(u32le(size(F)))
    h.update(content(F))
```

Манифест **не** включает каталоги, симлинки и сам PKGINFO.

### Поведение при установке (v1.1)

* Зависимости из `deps` разрешаются **автоматически** (dep-resolution
  v2): недостающие ставятся перед пакетом в topo-порядке; цикл или
  отсутствие пакета в индексе = отказ. `epkg install --no-deps`
  отключает резолвер (только предупреждения, как в v1.0).
* Скачивание возобновляемо: недокачанный файл лежит в кеше как
  `<filename>.part`; следующая попытка шлёт `Range: bytes=<size>-`.
  Ответ `206` → дописать; `200` (сервер не умеет Range) → качать
  заново; `416` или размер `.part` больше `size` из индекса →
  удалить и качать заново. До 4 попыток на зеркало; `.part`
  переживает перезапуск epkg. Корректность в любом сценарии
  гарантирует sha256 из индекса.

## 2. Индекс репозитория `index.json`

Обычный JSON (RFC 8259). Пример:

```json
{
  "epkg_index": 1,
  "repo": "my-repo",
  "packages": [
    {
      "pkgname": "hello",
      "pkgver": "1.0-r0",
      "pkgdesc": "Friendly hello demo for epkg",
      "arch": "any",
      "filename": "hello-1.0-r0.epkg",
      "sha256": "3d974abbf5e1b96d...",
      "size": 394,
      "deps": []
    }
  ]
}
```

Поля пакета:

| Поле | Тип | Назначение |
|---|---|---|
| `pkgname` | string | имя (обязательно) |
| `pkgver` | string | версия |
| `pkgdesc` | string | описание (для `epkg search`) |
| `arch` | string | архитектура (`any` — везде) |
| `filename` | string | имя файла в `packages/` |
| `sha256` | string | хеш **всего .epkg** — проверяется при скачивании |
| `size` | number | размер .epkg в байтах; используется докачкой и проверкой `.part` |
| `url` | string | *необязательно*: абсолютный URL, перекрывает зеркала |
| `deps` | array of string | зависимости с необязательными ограничениями версии (см. PKGINFO) |

Файлы пакетов лежат рядом: `<зеркало>/packages/<filename>`.
Исключение — поле `url`: если задано, пакет скачивается с него
напрямую (удобно для GitHub Releases):

```
https://github.com/<user>/<repo>/releases/download/v1.0/hello-1.0-r0.epkg
```

**Одна запись на имя.** epkg ищет пакеты по имени (`epk_index_get`
возвращает первую запись с таким `pkgname`), поэтому в индексе должно
быть ровно по одной записи на пакет — самая свежая версия. Старые
`.epkg`-файлы могут оставаться в `packages/` — просто не ссылайтесь на
них из `index.json` (генераторы `tools/build-sample.sh`,
`scripts/publish-sample-repo.sh` и тесты делают это автоматически).

## 3. Конфигурация `epkg.conf`

Построчный формат `key = value`, `#` — комментарии:

```
# список зеркал (первое рабочее используется)
mirror = https://raw.githubusercontent.com/<user>/<repo>/main
mirror = https://cdn.jsdelivr.net/gh/<user>/<repo>@main
mirror = http://192.168.1.50:8000          # локальное зеркало для QEMU

# каталоги
db    = /var/lib/epkg       # база установленных пакетов
cache = /var/cache/epkg     # кеш скачанных .epkg

# куда распаковывать пакеты (для chroot/QEMU-образов)
root  = /

# политика symlink'ов из пакетов:
#   deny (по умолчанию) — пропускать с предупреждением
#   keep                — создавать как есть (нужна поддержка в порте:
#                         epk_symlink; без неё — тихий откат к deny)
symlinks = deny

# PEM-бандл корневых сертификатов для HTTPS
ca    = /etc/epkg/ca.pem

# signify/ed25519 pubkey для проверки подписи индекса (см. раздел 5):
# путь к .pub-файлу ИЛИ inline base64 (начинается с "RWS...").
# Пусто = проверка выключена.
pubkey = /etc/epkg/repo.pub

# политика проверки подписи при epkg update (если pubkey задан):
#   strict (по умолчанию) — битая/отсутствующая подпись = отказ зеркала
#   warn                  — принять с WARNING
#   off                   — не проверять
audit = strict
```

Переменные окружения перекрывают файл:
`EPKG_CONF` (путь к конфигу), `EPKG_ROOT`, `EPKG_DB`, `EPKG_CACHE`,
`EPKG_CA`, `EPKG_SYMLINKS`, `EPKG_PUBKEY`, `EPKG_AUDIT`.

Путь поиска конфига: `$EPKG_CONF` → `/etc/epkg.conf` → `./epkg.conf`.

Глобальные ключи CLI перекрывают всё остальное: `--conf <файл>` —
явный конфиг, `--root <dir>` — корень образа, `--db <dir>` и
`--cachedir <dir>` — каталоги БД и кеша. Если при заданном `--root`
каталоги БД/кеша НЕ заданы явно, они размещаются внутри образа:
`<root>/var/lib/epkg` и `<root>/var/cache/epkg` (genesis-bootstrap,
см. README.md).

## 4. База установленных `<db>/`

```
<db>/installed/<pkgname>    три строки: pkgver \n pkgdesc \n deps
<db>/files/<pkgname>.list   по одному пути на строку (symlink тоже)
<db>/world                  world-файл: явно установленные имена
<db>/index.json             кеш индекса (обновляется `epkg update`)
<db>/index.sig              кеш подписи индекса (см. раздел 5)
```

### World-файл

Текстовый файл, по одному имени пакета на строку; пустые строки и
строки, начинающиеся с `#`, игнорируются. Ведётся автоматически:

* `epkg install a b` — дописывает `a`, `b` (без дублей);
* `epkg remove a` — вычёркивает `a`;
* `epkg upgrade x ...` — дописывает явно перечисленные имена.

`epkg upgrade` без аргументов обновляет ровно пакеты из world, у
которых версия в индексе новее установленной (`epk_vercmp`);
пакеты, подтянутые зависимостями, world не засоряют.

## Схема целостности

```
index.sig:   ed25519(index.json)   — защита самого индекса (см. раздел 5)
index.json:  sha256(весь .epkg)    — защита канала доставки
PKGINFO:     sha256(манифест файлов) — защита распакованного содержимого
```

Все три уровня проверяются на пути установки (подпись — при `epkg update`
и `epkg audit`, если pubkey закреплён). Расхождение = отказ установки
(или переход к следующему зеркалу на этапе скачивания). Докачка
безопасна по построению: `.part` от другого зеркала или другой
версии пакета не пройдёт финальную проверку sha256 и будет отброшен.

## 5. Подписи индекса (epkg audit): signify/ed25519

### Модель угроз

sha256 пакетов берётся ИЗ индекса — он защищает канал, но не источник.
Злоумышленник, контролирующий зеркало (или DNS/BGP между вами и
зеркалом), может подменить и `index.json`, и пакеты с согласующимися
хешами. Ed25519-подпись индекса закрывает это: ключ мейнтейнера
никогда не покидает его машину, а pubkey пользователя закреплён в
`epkg.conf`. Подменить индекс можно только владея секретным ключом.

TLS защищает канал до зеркала, но не само зеркало — подписи защищают
и при недоверенном зеркале (все зеркала взаимозаменяемы, порядок не
важен).

### Форматы файлов (совместимы с OpenBSD signify)

Открытый ключ `*.pub`:

```
untrusted comment: <комментарий>
<base64: "Ed" || keynum(8) || pubkey(32)>       # 42 байта -> 56 символов
```

Подпись `index.sig`:

```
untrusted comment: <комментарий>
<base64: "Ed" || keynum(8) || sig(64)>          # 74 байта -> 100 символов
```

Секретный ключ (расширение epkg; хранить ОФФЛАЙН):

```
untrusted comment: <комментарий>
<base64: "Ed" || keynum(8) || seed(32) || pubkey(32)>   # 74 байта
```

`keynum` — 8 случайных байт, общих для pub/sec/sig одной ключевой
пары (идентифицирует ключ в выводе `epkg audit` / `epkg-key fp`).
Подпись — Ed25519 (RFC 8032) над точными байтами `index.json`.

`epkg audit --repo <url>` и `epkg-key verify` проверяют blob'ы
независимо от имени/расположения файлов, а открытые ключи и подписи
`epkg`/`epkg-key` взаимозаменяемы с `signify -V`/`signify -S`.

### Правила epkg

* подпись делается на ТОЧНЫЕ байты index.json — публикация (git, raw)
  не должна менять файл (не «нормализуй» переводы строк после подписи);
* `epkg update` (strict): нет `index.sig` на зеркале или подпись
  невалидна — зеркало отбрасывается, пробуется следующее; все зеркала
  без валидной подписи = ошибка update (кеш НЕ обновляется);
* проверенная подпись и индекс пишутся в кеш атомарно
  (`<db>/index.sig`, `<db>/index.json`);
* `audit = warn` ослабляет strict до WARNING (для миграции репо на
  подписи), `audit = off` выключает проверку;
* криптография: своя реализация Ed25519 в `src/epk_ed25519.c`
  (C99, 26-битные лимбы, без 128-битных типов), векторы RFC 8032 и
  кросс-чек с OpenSSL — в тестах. Не constant-time: epkg подписывает
  оффлайн и проверяет публичные данные — для онлайновых протоколов с
  секретом в памяти этот код брать не стоит (см. README, Threat model).
